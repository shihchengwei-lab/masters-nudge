# 第八輪 Benchmark 正式報告

日期：2026-09-24

測試版本：Masters’ Nudge 0e8538f

## 結論

**B 臂呈現品味優勢，但尚未證明增加的成本值得。**正式契約判定 A、B 都是 9/12；在兩臂都通過、可盲評的八筆中，B 勝四筆、平手四筆、A 未勝。B 的總執行時間比 A 多 50%，非快取輸入 Token 多 77%。clap 的題目文字與驗收格式不一致，使 9/12 不能被當作乾淨的契約能力比較。

| 產品驗收條件 | 本輪觀測 | 判定 |
|---|---|---|
| 契約完成率不下降 | A 9/12、B 9/12；其中 clap 兩筆有驗收歧義 | 正式分數持平，契約結論需保留 |
| 品味勝率提高 | 可盲評八筆：B 勝 4、平 4、A 勝 0 | 有正向觀測，尚無因果證明 |
| 額外時間與 Token 值得 | B 多 1,119 秒、445,248 非快取輸入 Token | 尚未建立足以判定「值得」的效果證據 |

## 測試設計

六題各執行兩次，每次有 A、B 兩臂。Actor（實作模型）與 Provider（給結構回饋的模型）均為 GPT-6 Sol medium。A 臂沒有 Provider，沿用封存的 12 筆結果；B 臂啟用 Provider，以版本 0e8538f 獨立重跑 12 筆。只有 A、B 都通過任務驗收的樣本，才由 GPT-6 Astra 盲評程式結構品味。

這是固定題目與固定 A、重跑 B 的比較；B 沒有從同一份 A 中途狀態接續。B 與 A 的差異因此包含模型生成波動，不能全部歸因於 Provider。版本 0e8538f 相對前版 ba2ae7d 僅修改兩份同步的 Buddy prompt。

## 正式結果

| 指標，12 筆合計 | A：無 Provider | B：有 Provider | B 相對 A |
|---|---:|---:|---:|
| 契約通過 | 9/12 | 9/12 | 持平 |
| 可盲評樣本中的勝／平 | 0 勝、4 平 | 4 勝、4 平 | B 多 4 勝 |
| 總執行時間 | 2,240.0 秒 | 3,359.0 秒 | +1,119.0 秒，約 +50% |
| 非快取輸入 Token | 575,166 | 1,020,414 | +445,248，約 +77% |
| 快取輸入 Token | 7,296,512 | 10,948,352 | +3,651,840，約 +50% |
| 輸出 Token | 70,185 | 103,411 | +33,226，約 +47% |
| Provider 回饋／沉默 | 不適用 | 10／16 | 共呼叫 26 次 |

時間是 12 筆執行秒數的加總；Token 包含 Actor 與 Provider，不含重新盲評的 Judge。這些是用量，沒有換算成帳單金額或將總時間差當成 Provider 單獨耗時。

與前一版 B 相比，本次 B 的盲評由「B 勝 3、A 勝 1、平 4、不評 4」變為「B 勝 4、A 勝 0、平 4、不評 4」，契約仍為 9/12；但本次 B 的時間約多 11%、非快取輸入約多 11%、輸出約多 15%。兩次 B 都是獨立生成，且 ripgrep 第一次的驗收包裝有一處不影響通過判定的差異，不能把變化直接算成提示詞效果。

## 逐題判讀

| 題目 | 兩次契約結果與盲評 | 對結論的影響 |
|---|---|---|
| clap | A、B 兩次都未通過；均不盲評 | 原驗收要求 PR 的平列格式，Actor 收到的 issue 範例則是巢狀格式；詳見下方校準 |
| ripgrep | 第一次 A 通過、B 未通過；第二次 A 未通過、B 通過；均不盲評 | 未通過的兩筆都修改了明文禁止修改的既有測試；無法用來比較品味 |
| Vue 插槽 | 兩次兩臂都通過；第一次平手，第二次 B 勝 | 第二次回饋指出 Symbol key 的字串轉換邊界；第一次 B 的 key 規則有小幅重複，Provider 沉默 |
| Vue CSS | 兩次兩臂都通過；B 兩勝 | B 最終沿 ssContent 判定根節點；Provider 兩次提出的 activeBranch 方向反而有時序依賴，不能把勝利直接歸功於該建議 |
| Express | 兩次兩臂都通過；第一次 B 勝、第二次平手 | 第一次回饋建議用 Object.create(null) 排除快取鍵的原型干擾，最終實作與盲評理由相符；第二次兩臂均為 5/5 |
| Dark Reader | 兩次兩臂都通過；兩次平手 | 第二次正式程式碼修法相同；第一次有細節差異，但盲評未找到足以分勝負的結構優勢 |

四筆「不評」是 clap 兩筆與 ripgrep 兩筆，意思是至少一臂未通過契約，並非四筆 B 都失敗。本輪 B 實際未通過的是 clap 兩筆、ripgrep 第一次，共三筆。

## 契約校準補充：clap

正式 9/12 **維持原紀錄**。事後用封存補丁獨立重驗證，四份 A／B 都能輸出 Actor 收到的 issue 範例；B 第二次還通過三個不限定括號格式的「不折成 [ARGS]」情境，A 兩次都未通過這三項。依這組補充情境替換 clap 判定會得到 A 9/12、B 10/12，但它不是事前固定的正式契約，不能覆寫正式分數。

校準的關鍵是：原 PR 參考修補通過正式驗收，卻不符合交給 Actor 的 issue 範例。若暫時排除兩筆有爭議的 clap，其餘十筆 A、B 都是 9/10。校準使用封存補丁，在獨立工作樹執行原驗收、issue 範例與三個不限定括號格式的情境；這是事後分析，不能取代正式契約或盲評。

## 判定與後續

這輪有四筆 B 品味勝出，值得保留為正向訊號；其中兩筆 Vue CSS 的具體 nudge 方向有問題，且成本增幅明顯。因此目前**不宣告 Masters’ Nudge 已通過產品效果驗收，也不根據 clap 的 9/12 修改 Buddy prompt 契約排序**。下次正式測試應先讓 clap 的任務文字與驗收一致，並針對 CSS 的錯誤方向做同一中途狀態的有／無 nudge 對照，再評估效果是否值得成本。

**未驗證：**本輪沒有同一 Actor 中途狀態的因果對照；clap 補充校準沒有重新盲評；沒有實際金額資料。結論限於這 12 組封存 A／B 與既有盲評。
