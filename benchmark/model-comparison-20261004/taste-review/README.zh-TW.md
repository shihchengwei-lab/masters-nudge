# 程式碼品味複評：七臂覆核

覆核日期：2026-10-04。審查者：Codex。初評為 GPT-6 Astra medium 匿名盲評；複評已知組別與初評結果，核對同一批程式，沒有新增匿名評審票或重跑 Actor。最終品味採用複評。

**有些品味勝出被高估，但不是所有結構改造都在膨脹架構。重新審查 71 組有資格的比較後，65 組保留，6 組由勝出改為持平；沒有改判另一方勝出。**

原盲評的「勝出」只表示這兩份已過驗收的答案中相對較好，並不表示勝方已達絕對高品味。兩份各有明顯代價時，不應把某個局部優點升格為整體架構勝利。

高品味應看：在完整任務與既有相容行為成立的前提下，需要一起維護的資料、狀態、規則與時序是否實際變少。小補丁若把責任留在正確邊界，可以很好；新抽象若保住必要資訊、又消掉下游補救，也值得增加程式碼。

### 1. 保留資訊，卻繞成非同步重建：Proton 金鑰偏好 I2

分開保存兩種金鑰來源的加密偏好是正確方向，C2 只留合併值確實較弱。但 I2 在信任或金鑰類別改變時，為了取得一個 encrypt 值，重新呼叫完整金鑰模型建構。該建構還會執行非同步金鑰能力檢查，於是又需要取消旗標、refs 與偏好版本比對。這不是每次切換加密按鈕都重算；額外非同步流程發生在信任／金鑰類別變更。

同一批已封存答案的 I1 已示範較小的關係：保存兩種來源偏好，用同步的選擇函式取得有效值，沒有為這項投影重建完整模型。因此 I2 的「保留資訊」有收益，實作成本也明顯；與 C2 改判持平，不能只憑它符合一條準則就稱為整體高品味。

[I2：完整模型重建與取消保護](source-excerpts.zh-TW.md#source-1)；[I2：金鑰能力檢查](source-excerpts.zh-TW.md#source-2)；[I1：同步偏好選擇](source-excerpts.zh-TW.md#source-3)。

### 2. 把同步成本搬到相容邊界：Clap D1

巢狀集合讓每次出現的值自然成組，這個優點是真的。但題目同時要求既有平坦查詢、驗證與迭代行為繼續成立。D1 因此把原本的直接計數改成加總各組，既有 Values 與 OsValues 迭代器則要另外保存、更新 remaining，才能維持精確大小與雙向迭代。

E1 使用平坦值加群組範圍，確實需維護兩者一致；不過追加、開組與清除已集中在狹窄的幾個入口，並沒有散落成多套補丁。兩種方案各有成本，不能只因群組存在資料結構內就自動判 D1 勝。這裡是成本轉移，覆核持平；未以行數或未量測的效能下定論。

[D1：巢狀值與加總計數](source-excerpts.zh-TW.md#source-4)；[D1：迭代器剩餘數量](source-excerpts.zh-TW.md#source-5)；[E1：集中維護群組範圍](source-excerpts.zh-TW.md#source-6)。

### 3. 核心方向更好，旁邊卻新增另一套資料來源：OpenLibrary F1

題目本來就要求更新狀態與各類 updater，類別數量多不是過度設計的證據。F1 讓 updater 直接產生更新 state，確實比 I1 先產生舊命令再拆成 state 更直接。

但 F1 同時新增作者統計：掃描 provider.cache 或 docs_by_key 取得作品，算出 work_count、top_subjects、top_work；另一條可選 enrichment 又查 Solr、覆寫同一批欄位。新批次預設不 enrich，舊相容入口則開啟 enrich，作者資料的意義因此另依快取涵蓋範圍與入口模式決定。這項新增來源與模式成本，不能被「核心 state 更直接」蓋掉。

將封存的 get_works_of_author 原方法單獨執行：固定有兩部作品的資料集，快取分別持有 0、1、2 部時，方法分別只回傳 0、1、2 部。這驗證它讀取的是目前快取子集，並非作者全部作品的權威集合。此探針沒有重跑整個系統，亦不據此更動原契約完成分數。I1 保留舊命令轉接和外部統計也有代價，整體改判持平。

[F1：從快取列舉作品](source-excerpts.zh-TW.md#source-7)；[F1：兩條作者統計路徑](source-excerpts.zh-TW.md#source-8)；[單方法探針原始觀察](openlibrary-cache-probe.json)。

### 4. 小型整理也可能被高估

Ansible F2 消除的是函式執行期間的局部 invalid 旗標，不是持久錯誤資料模型；代價是把更大範圍的路徑與轉換錯誤一起歸為無效輸入。E2 的局部處理較精準，判持平。

[F2：較廣的例外攔截](source-excerpts.zh-TW.md#source-9)；[E2：局部失敗與轉換處理](source-excerpts.zh-TW.md#source-10)。

Flipt I2 共用 YAML 描述較好，但 C2 的輸出型別較嚴格、snapshot 單鍵表示較一致；兩者都還維護 Key/Keys 取捨。轉換函式集中本身不足以判整體勝出，判持平。

[I2：共用讀寫描述](source-excerpts.zh-TW.md#source-11)；[C2：限制輸出欄位](source-excerpts.zh-TW.md#source-12)；[C2：snapshot 單鍵正規化](source-excerpts.zh-TW.md#source-13)。

Element F2 額外捕捉未等待回呼中的刷新錯誤，原評語把這點當成 I2 不具備的保護。但實際 refreshDevices 已自行處理一般刷新失敗，兩份答案的 finally 都會清除登出載入狀態，尚不足以分出勝負。這組持平已有原先一名評審支持，本次沿實際呼叫路徑採用此判斷。

## 真正承重、因此保留的改善

- Element 的選取清單與更新函式成對提供：少量型別約束排除錯接，沒有增加第二份資料。
- Flipt I1 的雙格式在入口統一為同一份 Keys：匯入及 snapshot 不再各自判斷互斥欄位，抽象確實刪掉下游概念。
- Proton 重試保留「已發出的讀取」與「之後才欠下的刷新」的差別，或讓回應及計時器隸屬於原請求：這些狀態對應真正不同的事，增加它們有必要。
- Flipt I1 把對應快取失效放在修改成功之後：額外分流承擔真實時序，不能因程式較長就扣分。
- Clap I2 仍用平坦資料，但把自我覆寫集中在共同入口：消除入口清值、收尾補次數的配合，無須換成較大的資料架構。
- NodeBB C2 把嚴格刪檔錯誤留在本次圖片清理；F2 改了共用 file.delete，卻有既有上傳呼叫未等待它。局部修改的影響邊界反而較好。

## 評分斷點與更精準的判準

原六條判準已要求抽象實際消除概念，也不准依行數、helper 數量或測試數量判勝。問題主要在權衡：有些評語已列出新增成本，最後仍讓「資料表達更自然」「轉換集中」「不再有一個旗標」等局部優點決定總體勝負。另有一項勝出理由未充分沿既有呼叫路徑確認是否真的適用。

**部分結果確實符合「滿足評分形狀，卻沒有降低整體複雜度」的疑慮。原評審過度加權了局部準則。** 現有比較無法把這種現象單獨歸因於 Provider 引導或模型原有偏好；但可以直接修正過高的品味判斷，且不必否定那些已減少實際補救的改善。

更精準的總判準：**比較完整流程需要維護的必要資訊、狀態、規則與相容責任。新結構只有在保住要求、並實際減少總負擔時才判更好；只把補救搬到轉接、同步或另一套來源，不算架構提升。**
